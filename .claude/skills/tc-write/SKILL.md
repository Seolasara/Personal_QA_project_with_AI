# /tc-write
대상: `$ARGUMENTS` (ex: `ui 장바구니`, `api cart`). 비어 있으면 종류와 기능 범위를 묻는다.
작업 순서와 업무 규칙은 `.claude/agents/TC-Writer.md`를 따르고, TC 작성 포맷과 방법은 아래 규칙을 따른다.

# TC 작성 포맷과 방법 (구글 스프레드시트)
TC 원본은 구글 스프레드시트다. 저장소에는 TC md 파일을 두지 않는다. 

## 1. 공통 규칙 (UI-TC, API-TC)
1. **ID**: `UI_NN`(UI-TC 탭), `API_NN`(API-TC 탭).
   - 한번 정한 ID는 바꾸지 않는다. 새 TC는 그 시트의 가장 큰 번호 + 1을 받는다. 삭제나 폐기된 번호는 다시 쓰지 않는다.
   - 행은 **유저 플로우/기능 플로우 순서**에 맞는 위치에 삽입한다. 시트를 위에서 아래로 읽으면 수동 테스트 순서가 되고, ID는 번호 순서가 아니어도 된다.
   - 번호를 밀지 않으므로 테스트 마커, 백로그, Jira, 다른 TC 사전 조건의 참조 ID는 바뀌지 않는다. 기존 TC의 ID와 내용은 바꾸지 않는다.
2. **기능(UI)과 테스트 시나리오(API)**: "~ 시 ~ 확인" 형태로, 어떤 부분이나 기능의 어떤 상태나 동작을 확인하려는지 명확하고 간결하게 쓴다. "~ 확인"으로 끝낸다.
   - 입력값이 있으면 쓴다. ex: "수량 0 또는 음수 직접 입력 시 1로 보정 확인", "비밀번호 1자 또는 200자 입력 시 에러 메시지 노출 확인"
   - "·"를 쓰지 않는다. 둘 이상을 묶을 때는 "와", "과"로 잇는다.
3. **중요도(UI)와 Priority(API)**: High / Medium / Low. 사람은 QA plan 1.3(기능 단위 리스크 기준)으로 판단하지만, TC-Writer는 맥락이 부족하므로 아래 세부 기준으로 **그 케이스가 실패했을 때의 영향**을 매긴다(2026-10-10, AI 전용 기준). 기능의 리스크 우선순위는 출발점일 뿐 그대로 옮기지 않는다.
   - High: 실패하면 핵심 흐름(로그인 → 상품 조회 → 장바구니 → 결제)이 막히거나, 금액·주문·인증 데이터가 틀어진다. ex: 정상 로그인, 결제 완료, 합계 금액
   - Medium: 중요 기능의 일부가 틀어지지만 우회 경로가 있다. ex: 필터·정렬, 수량 보정, 입력 검증
   - Low: 표시, 문구, 보조 동작이라 흐름에 영향이 거의 없다. ex: 헤더 링크 노출, 안내 문구
   - 스펙 불일치라는 이유만으로 올리지 않는다(QA plan의 "스펙 불일치 한 단계 상향"은 TC 중요도에 쓰지 않는다).
4. **목적**(맨 뒤 열): 이 케이스를 왜 확인하는지, 그 확인으로 무엇을 보장하려는지 "~는지 확인" 형태로 한 문장으로 쓴다.
   - 절차(스텝)가 아니라 의도가 보여야 하며, 나중에 다른 사람이 봐도 왜 넣었는지 알 수 있어야 한다.
   - 기능과 같은 말을 반복하지 않는다. ex: "비밀번호를 5번 틀리면 계정이 잠기는지 확인", "빈 장바구니로 결제 단계에 진입하지 못하는지 확인"
5. **기대결과**는 스펙에 근거가 있는 것을 쓴다. 스펙이 정답이다.
   - 스펙에 없는 동작이 검증 대상이면 라이브로 확인한 동작을 기대결과에 쓴다(UI, API 공통). 이때 Note에 "확인 필요/실제 동작"을 쓰고, 백로그 안건(유형 E 스펙 미정의)으로 올리고, 결과 보고의 `ask_user`에 올려 사용자 판단을 받는다. 소스 코드에서 본 값은 쓰지 않는다.
   - 입력란 상태, 안내 문구 원문, 건수처럼 스펙에 없는 자세한 값은 쓰지 않고 동작 사실만 쓴다. ex: "이메일 입력 필드 하단에 얼럿 메시지 노출"
   - 어디에 무엇이 노출되는지 쓴다. "제거", "갱신" 같은 동작이 아니라 노출되는 상태로 쓴다. ex: "상품 행이 제거된 상태로 노출", "[Password] 필드 아래 에러 메시지 노출"
6. **Note**: 테스트할 때 꼭 필요한 내용만 쓴다. 스펙에 없는 동작을 기대결과로 쓴 경우에만 "확인 필요: ..."와 "실제 동작: ..."을 쓴다.
   - "확인 필요"와 "실제 동작"에는 검증하려는 기능의 동작 결과만 쓴다. ex: "확인 필요: 로그인 상태의 [Sign in] 링크 미노출은 스펙에 없음 / 실제 동작: [Sign in] 링크 미노출"
   - 다른 TC를 가리키는 문구(ex: "스텝 1~3은 UI_08과 동일")는 쓰지 않는다.
   - "(확인 필요)"를 기대결과에 쓰지 않는다. Note에 스펙 AC 번호나 "스펙 근거", 연속 실행 금지 같은 실행 주의, 백로그 번호, "Accept 헤더 필수" 같은 문구를 쓰지 않는다.
7. **표기**: 버튼은 [ ]로, 텍스트는 " "로 묶는다. 기능, 조건, 스텝, 기대결과, Note 모두 같다. ex: [Confirm] 버튼 클릭, "Payment was successful" 노출
8. **중복 금지**: 다른 TC와 같은 검증을 반복하지 않는다. 같은 규칙(ex: 수량 상한 보정)을 화면만 바꿔 다시 검증하지 않고 한 TC에서 한 번만 검증한다. 새 TC를 쓰기 전에 같은 대분류의 기존 TC 기대결과와 비교해, 겹치면 새 TC에서 빼거나 합친다. 겹침이 이미 있으면 작성하지 않고 보고한다.
9. **라이브 데이터 값**(상품명, 가격, 건수, id, 시각)은 루트 `CLAUDE.md` "판단 기준"대로 기대결과에 고정값으로 쓰지 않는다.

## 2. UI-TC (9열)
`ID | 대분류 | 기능 | 중요도 | 사전 조건 | 스텝 | 기대결과 | Note | 목적`

1. **ID**: 1번 공통 규칙
2. **대분류**: 메인, 로그인, 상품 조회, 장바구니, 결제, 로그아웃
3. **기능**: 공통 규칙 2번
4. **중요도**: 공통 규칙 3번
5. **사전 조건**: 테스트 전에 반드시 필요한 "상태"만 쓴다. 어느 페이지에서 시작하는지는 스텝 1번에 쓴다.
   - 그 테스트에서 자명한 조건은 쓰지 않는다. 로그인 TC에 "비로그인 상태"를 쓰지 않는다.
   - 데이터 존재 여부까지 구체적으로 쓴다. ex: "검색어 포함 상품 1건 이상 존재", "상품 재고 2개 이상 존재"
   - 사전 조건이 둘 이상이면 번호를 붙여 나눈다.
6. **스텝**: `[필드명] 필드 내 ~ 입력`, `[버튼명] 버튼 클릭` 형식으로 쓴다. 버튼·필드 이름은 실제 UI 표기를 쓴다.
   - 필드를 비울 때는 `값 미입력`.
   - 수동 테스트 시 순서대로 따라갈 수 있도록 이동 경로는 스텝 1번에 한 줄로 쓴다. ex: `메인 > 장바구니 > Sign in > BILLING ADDRESS`
   - 스텝은 장황하지 않게, 스텝 하나에 동작 하나만 쓴다. 스텝에 번호를 붙인다.
   - 스펙에 기준이 없는 엣지케이스(길이, 경계값 등)는 구체적인 값을 쓴다. 테스트하는 사람이 기준을 몰라도 따라 할 수 있어야 한다. ex: "1자 비밀번호 값 입력 (ex: “a”)"
7. **기대결과**: 스텝 번호와 맞춰 쓴다. 기대결과가 없는 스텝(ex: 페이지 이동)은 번호를 건너뛴다. 공통 규칙 5번을 따른다.
   - 값을 입력하는 스텝은 입력한 값이 노출되는지를 기대결과로 쓴다 (UI_03 형식).
   - 앞 TC의 흐름을 이어가는 TC(ex: UI_20 → UI_21)는 스텝을 앞 TC와 같은 형식으로 쓰고, 기대결과는 새로 검증하는 것만 쓴다. 앞 TC와 겹치는 기대결과는 뺀다.
8. **Note**: 공통 규칙 6번
9. **목적**: 공통 규칙 4번

예시: `UI_01 | 메인 | 메인 페이지 정상 접속 확인 | High | | 1. 페이지 진입 2. 탭 타이틀 확인 | 1. 페이지 정상 접속 2. 타이틀 노출 | | 서비스 진입점인 메인 페이지가 정상 접속되고 타이틀이 올바르게 노출되는지 확인`

## 3. API-TC (11열)
`ID | 대분류 | 테스트 시나리오 | 메서드 | 엔드포인트 | 사전 조건 | 요청 바디 | 기대결과 | Priority | Note | 목적`

1. **ID**: 1번 공통 규칙
2. **대분류**: 리소스 이름. ex: User, Brand, Category, Product, Cart, Payment, Invoice, Postcode
3. **테스트 시나리오**: 공통 규칙 2번
   - 응답 바디의 필드 타입을 확인하는 TC는 "응답 바디의 ... 필드 타입 확인"이라고 쓴다.
   - 필수 필드가 없는 요청은 "~ 시 "필드명" 필드 누락 확인"으로 쓴다. 무엇이 누락인지 "필드", "파라미터", "요청", "바디" 중 하나로 알 수 있으면 된다. ex: "계정 누락 요청으로 로그인 실패 확인"
4. **메서드, 엔드포인트**: 스펙(`api-docs.json`)의 표기를 그대로 쓴다.
5. **사전 조건**: UI의 사전 조건과 같은 규칙(테스트 전에 필요한 상태만, 자명한 조건은 생략, 데이터 존재 여부까지 구체적으로)이다. 번호(1. 2.)로 쓰고 불릿("- ")을 쓰지 않는다.
   - 다른 TC의 응답값을 쓰면 TC ID를 적는다. ex: "API_40 {{product_id}} 응답값 재사용"
6. **요청 바디**: JSON으로 쓴다. 바디가 없으면 `-`.
7. **기대결과**: 번호로 쓴다. 1번은 `HTTP status code: NNN`, 2번부터 응답 바디를 JSON으로 쓴다. 공통 규칙 5번을 따른다.
   - 값을 모르는 필드는 타입 문자열로 쓴다. ex: `"id": "string"`
   - 응답 바디에는 TC 목적을 확인하는 값과 요청에서 정해지는 값만 쓴다. 응답 전체를 붙여 넣지 않는다.
   - 시드 데이터(이름, 주소, 상품 목록, 전체 개수)와 매번 바뀌는 값(id, 시각)은 타입 문자열("string", "integer", "string | null" 등)이나 `{{변수}}`로 쓴다.
   - 다른 TC의 `{{변수}}`를 재사용하면, 그 변수를 저장하는 TC의 기대결과가 어느 항목에서 저장하는지와, 재사용하는 TC가 같은 대상을 가리키는지 확인한다.
   - 스펙에 정의되지 않은 상태코드나 응답 바디는 공통 규칙 5번대로 라이브로 확인한 값을 쓰고, Note에 "확인 필요: 스펙에 없어 라이브 응답 기준"으로 남긴다.
8. **Priority**: 공통 규칙 3번
9. **Note**: 공통 규칙 6번. "확인 필요: 확인할 내용"만 한 줄로 간결하게 쓴다.
10. **목적**: 공통 규칙 4번

예시: `API_03 | User | 비유효 비밀번호 로그인 실패 확인 | POST | /users/login | 1. 유효한 계정 존재 2. 계정이 잠기지 않은 상태 | {"email":"email","password":"password"} | 1. HTTP status code: 401 2. {"error": "Unauthorized"} | High | | 올바른 이메일이라도 비밀번호가 틀리면 로그인이 401로 거부되는지 확인`

## 4. 검수 표시와 마커
- 새로 쓴 행은 ID 뒤에 `*`를 붙이고 연한 노란색 배경으로 칠한다. 사용자가 시트에서 직접 검수한다.
- 검수가 끝나면 `*`와 배경색을 제거한다. 제거는 사용자가 요청할 때 한다.
- 테스트 함수에는 시트의 ID를 그대로 마커로 붙인다. ex: `@pytest.mark.tc("API_01")`. 마커 값은 시트 ID 열과 같아야 하고, `scripts/tc_marker_check.py`로 확인한다.
- 새 TC의 마커는 테스트 스크립트를 쓸 때 붙인다. 기존 TC의 ID가 바뀌지 않으므로 기존 마커는 갱신할 필요가 없다.

## 5. 자동화 판정
TC를 쓸 때 자동화할 수 있는지 판정한다. 아래 질문에 순서대로 답하고, 하나라도 "아니오"면 수동 TC다.
1. 기대결과를 기계가 판정할 수 있나 (사람의 감각, 주관 판단이 필요하지 않다)
2. 필요한 상태(데이터, 시간 경과, 외부 인증, 메일·기기)를 코드로 만들 수 있나
3. 반복 실행해도 안전한가 (되돌릴 수 없는 동작, 정리할 수 없는 데이터가 없다)
4. 단독 실행 3회에서 결과가 같은가 (스크립트 작성 단계에서 확인한다)
5. 유지 비용이 수동 비용보다 작은가 (1회성 확인, 자주 바뀌는 신규 화면이 아니다)
- 수동 TC는 결과 보고에 질문 번호를 사유로 붙여 올린다. ex: "UI_NN 수동(2: Google 실제 로그인)"
- 판정이 애매하면 자동으로 두고, 4번은 Script-Writer가 "수동 후보"로 보고한다.
- 1~3번 사례: 디자인·문구 자연스러움(1), 실제 Google 로그인, CAPTCHA, 메일 수신(2), 실제 PG 결제, 운영 데이터 변경(3)

## 6. 작성 후 점검 체크리스트
초안을 보고하기 전에 한 번 훑는다. TC마다 하지 않고 배치당 한 번, 전체의 10% 정도를 표본으로 확인한다.

**1. 기계 점검 (`scripts/tc_lint.py --type ui|api`, 입력은 초안 JSON)**
- 초안 JSON의 키는 시트 헤더와 같게 쓴다. UI: 기능, 목적, 중요도, 사전 조건, 스텝, 기대결과, Note. API: 테스트 시나리오, 목적, 메서드, 엔드포인트, 사전 조건, 요청 바디, 기대결과, Priority, Note
- 점검 항목
  - [ ] 기능 또는 시나리오에 "·"가 없고 "~ 확인"으로 끝난다
  - [ ] 중요도(Priority)가 High / Medium / Low 중 하나다
  - [ ] 목적이 비어 있지 않고 "~는지 확인"으로 끝난다
  - [ ] 기대결과에 "(확인 필요)"가 없다
  - [ ] Note에 "스펙 근거", 연속 실행 금지, 백로그 번호, Accept 헤더 문구, 다른 TC를 가리키는 문구가 없고, 확인 필요 문구는 "확인 필요:"로 시작한다
  - [ ] 사전 조건이 여러 줄이면 번호 형식이고, 불릿("- ")이 없다
  - [ ] UI: 버튼 이름에 [ ]가 있고, 스텝과 기대결과가 번호 형식이다
  - [ ] UI: 기대결과가 "제거", "갱신" 같은 동작으로 끝나지 않는다
  - [ ] API: 기대결과가 번호 형식이고 1번이 상태코드이며 응답 바디가 JSON이다
  - [ ] API: 누락 TC는 이름에 "필드 누락"(또는 파라미터, 요청, 바디)이 있고, 타입 확인 TC는 "응답 바디의 ... 필드 타입 확인"이 있다

**2. 판단 점검 (사람이나 LLM이 표본으로 확인한다)**
- [ ] 기능명을 보면 무엇을 확인하는지 바로 알 수 있다 (입력값이 있으면 기능명에 있다)
- [ ] 목적이 절차가 아니라 "왜 확인하는지" 의도를 말한다
- [ ] 기대결과가 어디에 무엇이 노출되는지 명확하다
- [ ] 스펙에 기준이 없는 엣지케이스는 스텝에 구체적인 값이 있다
- [ ] 스펙에 없는 동작을 기대결과로 썼다면 Note에 "확인 필요/실제 동작"이 있고, 백로그 안건으로 올렸고, 결과 보고의 `ask_user`에 있다
- [ ] 같은 대분류의 기존 TC와 같은 규칙을 다시 검증하지 않는다 (화면만 다른 중복 포함)
- [ ] 앞 TC에서 이어지는 TC는 새로 검증하는 기대결과만 쓰고 스텝은 앞 TC와 같은 형식으로 쓴다(Note에 "앞 TC와 동일" 같은 문구는 쓰지 않는다)
- [ ] 새 행은 `*`와 노란 배경으로 표시했고 pytest 마커는 건드리지 않았다
