# /script-write
대상: `$ARGUMENTS` (ex: `UI_24, UI_25`, `API_40-API_45`). 비어 있으면 TC ID를 묻는다.
작업 순서와 업무 규칙은 `.claude/agents/Script-Writer.md`를 따르고, 스크립트 작성 포맷과 방법은 아래 규칙을 따른다.

# 스크립트 작성 포맷과 방법 (pytest)
TC 원본은 구글 시트이고, 테스트 하나가 TC 하나다. 종류별 구조와 컨벤션(셀렉터, client, schema, fixture)은 각 폴더 `CLAUDE.md`를 따른다.

## 1. 공통 규칙 (UI, API)
1. **마커**: 테스트 함수에 시트 ID를 그대로 붙인다. ex: `@pytest.mark.tc("UI_24")`. 같은 TC에 마커가 붙은 함수는 하나만 둔다.
2. **기존 테스트 재사용**: 같은 TC를 이미 검증하는 기존 테스트가 있으면 새 함수를 만들지 않는다.
   - 기존 테스트가 시트 TC의 요청과 기대결과에 맞으면 마커를 붙이고 `#tcNN` 주석은 지운다. 맞지 않으면 시트 TC에 맞게 고치고 보고에 적는다.
   - API 기존 테스트의 `#tcNN` 주석은 옛 번호라서 믿지 않고 시트 내용으로 대조한다.
3. **파일과 순서**: 기능별 `*_test.py`에 두고, 파일과 함수 이름은 기존 파일의 규칙을 따른다.
   - 파일 안의 테스트는 TC ID 번호 오름차순으로 둔다. 새 테스트를 파일 끝에 붙이지 않고 번호 순서에 맞는 자리에 넣는다.
   - 순서가 어긋난 기존 테스트는 같은 파일 안에서 함께 재정렬하되 내용은 바꾸지 않는다.
4. **어설션**: 기대결과의 모든 항목을 어설션으로 옮긴다. 기대결과가 3개면 어설션도 3개 이상이다.
   - 문구 대신 존재 여부만 보거나, 상태코드만 보고 바디를 보지 않는 식으로 약하게 쓰지 않는다.
5. **역할 분리**: 셀렉터, 요청 구성, 응답 모델은 테스트 본문에 두지 않고 Page Object, client, schema에 둔다. 테스트 본문에는 행위와 어설션만 둔다.
6. **독립성**: 테스트는 단독으로 실행해도 통과해야 한다. 테스트 간 상태 의존을 만들지 않고, 만든 데이터(장바구니, 인보이스 등)가 다음 테스트에 영향을 주지 않게 한다.

## 2. xfail 규칙
- 루트 가드레일의 "백로그에 등록된 real-bug만 strict xfail로 고정"을 쓰는 방법이다. 새로 발견한 실패에 xfail을 붙이기 전에는 반드시 triage → 백로그 등록이 먼저다.
- `xfail(strict=True, reason="...백로그 #N 또는 이슈 키...")`로 표시한다. 버그가 고쳐지면 XPASS로 실패 처리되어 바로 드러난다.
- 스펙 불일치가 테스트 일부일 때는 테스트 전체에 xfail을 붙이지 않는다. 나머지 어설션을 먼저 두고, 불일치 비교만 `pytest.xfail("백로그 #N: ...")`로 처리한다. 테스트 전체가 불일치 하나만 검증하면 `xfail(strict=True)`를 쓴다.
- xfail을 붙인 테스트는 `--runxfail`로 실제 실패 원인을 확인한다. import 누락 같은 코드 오류도 xfail로 가려진다.
- 간헐 결함(재현성 "간헐")은 strict xfail로 고정하지 않는다. 백로그에 "회귀 대상"으로 추적한다(`.claude/guides/issue-severity.md`).
- 교훈: xfail로 고정하기 전에 테스트 클라이언트 설정(헤더 등) 문제가 아닌지부터 의심한다. 사례는 `api-demo/CLAUDE.md`.

## 3. 실행 규칙
- 새로 쓴 테스트만 파일과 함수를 지정해 실행한다. ex: `pytest -m "tc"`가 아니라 `pytest tests/cart_test.py::test_name`
- 실행은 각 폴더의 venv에서 해당 폴더 기준으로 한다.
- 같은 테스트를 실패 후 반복 실행해 통과를 만들지 않는다. 재실행은 원인을 고친 뒤 1회만 한다.
- 자동화가 어려워 보이는 TC(슬라이더, 애니메이션, 외부 연동 등)는 단독 실행 3회로 안정성을 확인한다. 결과가 흔들리거나 `tc-write` SKILL.md "자동화 판정"의 1~3번에 걸리면 억지로 쓰지 않고 "수동 후보"로 사유와 함께 보고한다.
- 병렬 배치에서는 리포트가 서로 덮어쓰지 않게 출력 경로만 임시 경로로 바꾼다. ex: `--json-report-file=<임시>/report.json --html=<임시>/report.html --output=<임시>`. `-o addopts=""`는 실패 시 trace 저장까지 꺼서 원인을 못 보므로 쓰지 않는다.
- 전체 실행은 사용자가 허락했을 때만 다음 순서로 한다.
  - 각 폴더에서 전체 테스트를 1회 실행한다.
  - UI는 `playwright-demo/.venv/bin/python scripts/gen_test_report.py`로 `test-results/test-report.md`를 만든다. API는 아직 리포트 스크립트가 없어서 pytest 결과 요약을 보고에 쓴다.
  - 리포트에 실패 분류와 근거를 붙여 보고한다.

## 4. 작성 후 점검 체크리스트
보고하기 전에 확인한다. 기계 점검은 새로 쓴 파일 전체에, 판단 점검은 배치당 한 번 새 테스트의 10% 정도를 표본으로 한다.

**1. 기계 점검**
- `python3 scripts/script_lint.py <새로 쓰거나 고친 테스트 파일>`: 오류 0건이어야 한다.
  - 점검 항목: 마커 유무와 형식, 마커 중복, 어설션 유무, `wait_for_timeout`/`sleep`, skip, xfail 조건, 비밀번호 하드코딩, XPath/nth, 테스트 본문의 셀렉터, API의 async/직접 httpx
- 시트 CSV를 루트 `CLAUDE.md`의 CSV 주소로 임시 경로에 받아 `python3 scripts/tc_marker_check.py --ui <UI-TC.csv> --api <API-TC.csv>`를 실행한다. 시트에 없는 마커와 중복 마커가 없어야 한다. 받은 CSV는 저장소에 남기지 않는다.
- xfail을 붙인 테스트는 `--runxfail`로 한 번 실행해 실패 원인이 백로그 항목과 같은지 확인한다.

**2. 판단 점검**
- [ ] 기대결과의 모든 항목이 어설션으로 옮겨졌고, 약해진 어설션이 없다
- [ ] 통과하도록 TC와 다른 값을 쓰지 않았다
- [ ] 기존 Page Object, client, fixture를 재사용했고, 같은 기능의 중복 정의가 없다
- [ ] 단독 실행으로 통과하고, 만든 데이터가 다른 테스트에 영향을 주지 않는다
- [ ] 실패 분류가 근거와 맞다
