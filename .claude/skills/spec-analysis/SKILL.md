# /spec-analysis
대상: `$ARGUMENTS` (ex: `ui 장바구니`, `api`, `ui update`). 비어 있으면 종류를 묻는다.
- `update`: 변경분 분석이다. 기준 커밋 이후 서비스 변경을 분석 문서에 반영한다.
- 기능 범위(ex: `ui 장바구니`): 그 기능을 분석한다. 분석 파일이 이미 있으면 덮어쓰지 않고 바뀐 부분만 고친다.
- 종류만(ex: `api`): 개요 파일에 분석 기준이 없으면 처음 분석이다.
작업 순서와 업무 규칙은 `.claude/agents/Document-Analyzer.md`를 따르고, 분석 포맷과 방법은 아래를 따른다.

# 분석 포맷과 방법
기획·요구사항 분석만 쓴다. 기존 TC 번호, TC 시트 반영 현황은 쓰지 않는다(TC-Writer 담당).

## 1. 파일 구성
대상 영역마다 개요 파일 1개와 기능별 파일 N개로 나눈다. 저장 위치는 `.claude/docs/spec analysis/ui/`(UI) 또는 `api/`(API)다.
1. 개요 파일 `00_<영역>-overview.md` (ex: `ui/00_ui-overview.md`, `api/00_api-overview.md`)
   - 메인 파일이다. 파일명이 `00_`으로 시작해 목록 맨 위에 온다. 첫 줄에 "이 파일이 메인"이라고 쓴다.
   - 대상, 근거 자료, 판단 기준
   - 분석 기준(2번)
   - 기능별 분석 파일 목록
   - 리스크 목록: 영역 전체 리스크를 **우선순위 높은 순**으로 한 표에 모은다. 열은 ID, 우선순위(높음/중간/낮음), 리스크, 예상 영향 범위, 상세 링크. 번호(R1, R2…)는 우선순위 순으로 매기고 기능 파일에서도 같은 번호를 쓴다. 우선순위 기준(틀어질 가능성 × 영향 범위)을 표 위에 적는다.
   - 제외(와 제외 사유), 확인 못 한 것
2. 기능별 파일 `<영역>-<기능>.md`: 아래 섹션을 이 순서대로 쓴다.
   - 1. 기능 목적
   - 2. 핵심 흐름 (단계별 번호)
   - 3. 리스크 상세 (개요 표의 ID 사용, 항목마다 근거 한 줄: 어떤 화면/스펙에서 확인했는지)
   - 4. 테스트 범위 (포함)
   - 5. TC 작성 입력값 (후보: 대상 화면, 입력 후보, 기대 결과 후보)
   - 6. 변경 이력 (3번 형식. 변경이 생길 때만 만든다)

## 2. 개요 파일의 "분석 기준" 블록
변경분 분석의 출발점이다. 개요 파일의 "분석 개요" 안에 둔다.
- 서비스 레포 기준 커밋: 해시 7자 이상, 커밋 날짜. 기록 없이 만든 기존 분석은 분석일 직전 커밋을 쓰고 "(추정)"을 붙인다.
- 분석일
- 감시 경로(서비스 레포 `testsmith-io/practice-software-testing` 안의 경로)
  - 스펙: `docs/user-stories/`, `docs/features.md`
  - UI: `sprint5/UI/src/app/`, `sprint5/UI/src/assets/i18n/en.json`
  - API: `sprint5/API/storage/api-docs/api-docs.json`, `sprint5/API/routes/`, `sprint5/API/app/`
  - 기준 변형은 `sprint5`다. `sprint5-with-bugs` 같은 다른 변형의 변경은 분석하지 않는다.

## 3. 기능별 파일의 "6. 변경 이력"
변경이 생길 때마다 맨 위에 추가한다(최신이 위).
- `### YYYY-MM-DD 변경 요약 (기준 커밋 aaaaaaa → bbbbbbb)`
  - 변경 내용: 파일, 요지
  - 영향 기능과 영향 범위: 화면 또는 API
  - 리스크: 개요 표의 ID(신규면 새 ID)와 우선순위 변화
  - 사이드이펙트: 같은 코드를 쓰는 다른 기능, 공통 컴포넌트, 데이터 영향
  - 확인 필요: diff로 확정할 수 없는 것과 확인 방법
  - TC-Writer 후속: 새로 쓰거나 고칠 후보 시나리오(TC 번호는 쓰지 않음)

## 4. 변경분 분석 방법
1. 감시 경로로 diff를 좁히고 변경 파일을 기능에 매핑한다(경로, 컴포넌트명, 라우트).
2. 변경된 함수, 컴포넌트, 값의 사용처를 `Grep`으로 찾아 영향 범위와 사이드이펙트를 정한다.
3. 스펙(`docs/user-stories/v5.md`)이 바뀌었으면 AC 단위로 변경 전후를 비교해 기대결과가 바뀌는 기능을 먼저 정리한다. 스펙 변경은 영향이 가장 직접적이므로 소스 변경보다 먼저 쓴다.
4. 리스크 우선순위 기준(틀어질 가능성 × 영향 범위)으로 개요 표를 다시 정렬하고, 새로 생긴 리스크에는 새 R번호를 매긴다. 기존 번호는 바꾸지 않는다.
5. 확정할 수 없는 영향은 '후보'로 쓰고 확인 방법을 적는다.
6. 감시 경로에 변경이 없으면 분석 파일과 기준 커밋을 바꾸지 않는다. 대신 분석 로그에 "변경 없음"을 남긴다.

## 5. 분석 로그
분석이 끝나면 처음 분석, 변경분 분석, 변경 없음 모두 `.claude/docs/spec analysis/analysis-log.md` 맨 위에 항목을 추가한다(최신이 위).
- 첫 줄이 한 줄 요약이다. 어느 부분에서 어떤 변경이 있었는지 먼저 보이게 쓴다.
  - `## YYYY-MM-DD [ui|api] 모드 — 요약`
  - 요약 ex: `결제 Billing 주소 필드의 invalid 스타일 조건 변경 (영향 낮음)`, `변경 없음`, `처음 분석: 로그인, 장바구니 등 6개 기능`
- 그 아래 불릿 3개 이내
  - 기준 커밋: aaaaaaa → bbbbbbb (커밋 N개, 감시 경로 변경 파일 M개). 변경 없음이면 확인한 HEAD를 쓴다.
  - 갱신한 파일: 없으면 "없음"
  - 상세 위치: 기능 파일의 "6. 변경 이력" 항목

노션에도 매번 남긴다. 변경이 없어도 남긴다. 대상은 "AI Report" 아래 "Document-Analyzer 분석" DB(`collection://2cbd9aee-5684-45c4-841a-fc6e0efa8a2f`)이고 행 하나가 분석 한 번이다.
- 제목: `YYYY-MM-DD [ui|api] 모드 — 한 줄 요약` (분석한 날짜 포함. 로그의 첫 줄과 같은 내용)
- 속성: 날짜(분석일), 기능명(영향받은 기능, 없으면 "전체" 또는 "해당 없음"), 로컬 파일(갱신한 파일 경로, 없으면 `analysis-log.md`), 상태(완료), 요약(한 줄 요약)
- 본문: 커밋이나 PR이 올라온 날짜를 포함해 쓴다. `git log --format='%h %cs %s' <기준>..HEAD`로 구한다.
  - 변경 목록: `YYYY-MM-DD 커밋 해시 또는 PR #번호 제목`을 날짜순으로, 영향 있는 항목 먼저
  - 분석한 범위: 기준 커밋 → 확인한 HEAD(각각의 커밋 날짜)
  - 변경이 없으면 "감시 경로 변경 없음"과 확인한 범위, 다른 변형(sprint5-with-bugs 등)에만 있던 커밋이 있으면 그 날짜와 PR 번호만 적는다.
  - 영향 기능과 리스크 요약, TC-Writer 후속 후보

## 6. 완료 기준
- 개요와 기능별 파일의 섹션이 모두 채워졌거나, 빈 섹션에 이유가 적혀 있다.
- 개요의 리스크 표가 우선순위 순이고 모든 리스크가 영향 범위와 함께 들어 있다.
- 분석 로그에 항목이 추가되었다(변경 없음 포함).
- 변경분이면 "분석 기준"의 기준 커밋과 분석일이 새 값으로 바뀌었고, 변경 이력에 영향 기능, 범위, 리스크, 사이드이펙트, TC-Writer 후속이 모두 있다.
