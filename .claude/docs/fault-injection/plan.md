# 결함 탐지율 검증 계획 (sprint5-with-bugs)
작성 2026-10-16, 방식 변경 2026-10-16(온라인 with-bugs 실행 → 로컬 sprint5 결함 주입). 상태: 5단계 진행 중.

## 1. 목적
- 우리 테스트가 결함이 있을 때 실제로 실패하는지 확인합니다. 지금까지는 "테스트가 통과한다"만 확인했고, "결함을 잡는다"는 확인하지 않았습니다.
- 잘못 만들어져 결함을 놓치는 TC나 스크립트(통과만 하는 테스트)를 찾고, TC의 빈틈을 숫자로 보여 줍니다.
- 계기: 회고에서 AI로 만든 TC와 스크립트가 결함을 못 거르고 통과만 하는 것은 아닌지, 정확성과 신뢰성이 떨어져 비즈니스 리스크로 이어지는것이 아닌지에 대한 고민이 출발점.

## 2. 대상과 정답지
- 방식: 로컬에 띄운 `sprint5`(운영 사이트와 같은 버전)에 정답지의 버그를 하나씩 직접 심고, 우리 테스트가 실패하는지 봅니다(결함 주입).
- 방식을 바꾼 이유(2026-10-16 소스 비교)
  - 처음 계획은 온라인 버그 사이트(`with-bugs.practicesoftwaretesting.com`)에 테스트를 그대로 돌리는 것이었습니다.
  - 그런데 `sprint5-with-bugs`는 sprint5에 버그만 심은 버전이 아니라 오래된 별도 빌드였습니다. UI 소스 259개 파일이 다르고, 화면 요소 표시(`data-test`) 98개가 sprint5에만 있으며, 우리 UI 테스트가 쓰는 표시 62개 중 15개(ex: `filter_completed`, `street`, `postal_code`)가 없습니다. API도 앱 코드 95개 파일과 스펙 문서가 다릅니다.
  - 그대로 돌리면 버그와 무관하게 대부분 실패해서 탐지율이 거짓으로 높게 나옵니다.
- 정답지: 서비스 레포 `sprint5-with-bugs/testSessions/listOfBugs.md`(94건, 커밋 `ae7caec` 기준). 어떤 증상을 심을지 고르는 목록으로만 씁니다.
- 기준 원칙: 기대 동작의 기준은 계속 `sprint5`와 스펙입니다(루트 `CLAUDE.md` 판단 기준).
- 서비스 소스는 서비스 레포를 작업용 폴더에 받은 사본만 고칩니다. 운영 사이트와 GitHub 원본은 건드리지 않고, 우리 저장소에는 서비스 코드를 넣지 않고 패치 기록만 남깁니다.

## 3. 진행 단계
1. 정답지 분류(심을 버그 선정)
   - 94건을 범위 안과 범위 밖으로 나누고, 범위 안 버그마다 "그 버그가 있으면 실패해야 하는 TC"를 적습니다.
   - sprint5에 같은 증상을 낼 수 없는 버그(with-bugs에만 있는 화면, 기능)는 제외 사유를 적습니다.
   - 결과를 보기 전에 분류를 고정합니다. 실행 결과에 맞춰 기준을 바꾸지 않습니다.
2. 로컬 구성
   - 서비스 레포 `docker-compose.yml`(`SPRINT=sprint5`)로 UI(`localhost:4200`), API(`localhost:8091`)를 띄우고 DB를 시드 데이터로 채웁니다.
   - UI·API 테스트 계정(customer2, customer3)으로 로그인되는지 확인합니다.
   - DB를 초기화(`php artisan migrate:fresh --seed`)한 뒤에는 반드시 API 캐시를 비웁니다(`php artisan cache:clear`). 초기화하면 ID가 새로 만들어지는데 캐시에 옛 ID가 남아 목록과 단건 조회가 엇갈립니다(2026-10-15 확인).
3. 테스트 주소 설정
   - API: 접속 주소를 환경변수(`API_BASE_URL`)로 바꿉니다.
   - UI: 주소가 코드에 고정돼 있어 환경변수로 바꿀 수 있게 테스트 코드를 고칩니다(기본값은 지금 운영 주소).
4. 기준 실행(승인 지점)
   - 버그를 심지 않은 로컬 sprint5에 UI·API 전체를 한 번 돌립니다. 운영 사이트와 같은 결과(기존 결함 테스트만 실패)가 나와야 합니다.
   - 이유 없이 실패하는 테스트는 로컬 환경 문제로 보고 고치거나 측정에서 뺍니다.
   - 기준 실행 결과(2026-10-15): API 85건 중 실패 12건, UI 59건 중 실패 9건·오류 2건
     - 기존 결함 테스트(`issue` 마커) 19건(UI 7, API 12)은 운영과 같은 결함으로 실패합니다.
     - 로컬에서만 실패: `test_login_form_elements`(UI_40, Google 버튼은 운영 빌드에서만 표시), `test_billing_required_field_disables_proceed`(UI_33, 우편번호 재조회 응답이 오지 않음. 원인 추정: 같은 값 재입력 시 조회 생략, 6단계 전에 확인)
     - 정리 단계 오류: `test_cart_check`, `test_cart_quantity_from_detail`(본문은 통과, 장바구니 비우기에서 조회 응답 없음. 원인 미확인)
   - 판정 제외 기준: 기준 실행에서 이미 실패한 테스트는 버그를 심은 뒤 실패해도 "발견"으로 세지 않습니다. 정리 단계 오류는 본문 결과로 판정합니다.
5. 결함 주입(버그마다 반복)
   1. sprint5 사본의 해당 코드를 그 증상만 나도록 최소한으로 틀리게 바꿉니다. with-bugs 코드는 증상 참고용으로만 봅니다.
   2. 화면이나 API로 증상이 실제로 났는지 먼저 확인합니다(제대로 심지 못한 버그를 "발견 실패"로 세지 않기 위해).
   3. 잡아야 할 TC, 같은 기능의 테스트, smoke를 돌립니다.
   4. "발견 / 발견 실패"를 기록하고, 코드를 원래대로 되돌린 뒤 smoke로 기준 상태를 확인합니다.
   - 한 번에 한 버그만 심습니다. 바꾼 내용은 `patches/`에 버그마다 패치 파일로 남깁니다.
   - 마지막에 몇 건은 전체 실행으로 다른 테스트가 우연히 잡는지도 봅니다.
6. 판정과 정리
   - 탐지율과 빈틈을 계산하고, 발견 실패한 버그는 원인(TC 없음, TC가 약함, 스크립트가 약함)을 봅니다.
   - 운영 사이트에서도 실패하는 기존 결함 테스트(`issue` 마커)는 구분해서 숫자가 부풀지 않게 합니다.
   - 결과와 빈틈 목록을 이 폴더에 남깁니다. TC 보강은 결과를 보고 따로 정합니다.

## 4. 범위 기준 (1단계에서 고정)
- 범위 밖
  - QA plan의 Out-of-Scope 기능: 회원가입, 프로필, 비밀번호 찾기, 문의, 관리자, 이메일
  - Firefox·Edge 전용 증상: 테스트는 Chromium만 실행합니다.
  - 접근성(라벨, 대비)과 보안 정밀 점검: QA plan의 범위 밖 항목입니다.
- 범위 안: 메인(검색, 필터, 정렬), 카테고리, 상품 상세, 장바구니, 결제, 로그인·로그아웃, API의 브랜드, 카테고리, 상품, 장바구니, 인보이스, 결제, 로그인

## 5. 지표
- 탐지율 = 실패로 잡은 범위 안 버그 수 / 범위 안 버그 수
- 설계 빈틈 비율 = 대응 TC가 없는 범위 안 버그 수 / 범위 안 버그 수(실행 전 1단계에서 나옴)
- 실행 빈틈 = 대응 TC가 있는데 통과한 버그(잘못 만든 TC나 스크립트 후보)
- N/A로 실행하지 않은 TC가 대응하는 버그는 따로 셉니다.

## 6. 주의
- 로컬 환경이라 운영 사이트에 부담이나 데이터가 남지 않습니다. 결제 확정, 계정 잠금도 로컬 DB에서만 일어납니다.
- 계정 잠금 버그(정답지 #21)를 심을 때는 로그인 실패 TC를 그 버그에서만 돌리고, 끝나면 로컬 DB의 잠금을 풉니다.
- 정답지는 서비스 제작자가 공개한 목록이라 sprint5에 같은 증상을 내는 방법이 여러 가지일 수 있습니다. 어떻게 심었는지에 따라 결과가 달라질 수 있으므로 패치와 기대 증상을 함께 기록합니다.
