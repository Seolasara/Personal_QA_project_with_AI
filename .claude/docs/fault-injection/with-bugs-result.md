# 결함 주입 결과
버그를 일부러 심어서, AI 기반 QA 워크플로우가 만든 TC와 테스트 스크립트가 결함을 실제로 잡는지 확인한 결과입니다. 계획은 `plan.md`, 버그 분류와 대응 TC는 `with-bugs-scope.md`에 있습니다.
측정 2026-10-16~17. 버그별로 심은 코드는 `patches/`에 있습니다.

## 1. 결론
결론은 목적에 따라 두 가지입니다.

1. AI 기반 QA 워크플로우의 정확성과 신뢰성: 대응 TC가 있는 버그 기준
   - 대응 TC가 있는 버그 13건 중 11건을 잡았습니다(탐지율 84.6%).
   - 잡은 11건은 모두 그 버그를 확인하는 어설션에서 정확한 이유로 실패했습니다(ex: 합계 $40.23 기대, $0.00).
   - 놓친 2건은 TC가 아니라 스크립트가 TC보다 덜 엄격했기 때문입니다.
     - #9: 제목을 부분 일치로 찾음
     - #27: 확인 값이 테스트 데이터에 기댐
   - 즉 TC가 있는 곳에서 워크플로우는 대체로 믿을 만하고, 보강할 곳은 스크립트 작성 규칙(문구는 정확 일치, 필터는 결과가 실제로 달라지는 값)입니다.
   - 두 스크립트를 고친 뒤 같은 버그를 다시 심자 모두 잡았습니다(13/13, 9번).
2. 이 프로젝트의 보강 근거: 측정 대상 전체 기준
   - 측정 대상 26건 중 13건을 잡았습니다(탐지율 50.0%).
   - 놓친 13건 중 11건은 TC 설계가 미흡해 대응 TC가 없었습니다.
     - 비슷한 TC가 다른 조건만 지나감: 3건
     - 비슷한 TC가 요소의 노출까지만 확인: 4건
     - 그 요소를 다루는 TC가 아예 없음: 4건
   - 대응 TC가 없는 13건 중 다른 테스트가 우연히 잡은 건 2건뿐이고, 그마저 실패가 시간 초과 형태로 나와 원인을 알려 주지 못했습니다.
   - 즉 지금 TC는 기능의 기본 흐름 위주라, 상태와 화면 조합, UI 문구, 화면 모양에서 결함을 놓칩니다. 보강 후보는 7번에 있습니다.
   - 보강한 뒤 다시 심어 보니 놓친 버그 중 7건을 더 잡아, 전체 26건 중 22건(84.6%)을 잡습니다. 남은 4건은 시각 버그입니다(10번).

## 2. 어떻게 측정했나
1. 정답지 고르기
   - 서비스 제작자가 공개한 버그 목록 94건 중 우리 테스트 범위(로그인, 상품 조회, 장바구니, 결제와 해당 API) 안 28건을 골랐습니다. 테스트 환경에서 발생 조건을 만들 수 없는 버그(ex: 테스트 계정에 없는 데이터가 필요한 버그)는 범위 밖으로 둡니다.
   - 판정할 수 없는 2건은 뺐습니다: #47(대응 TC가 원래 실패하는 기존 결함 TC뿐), #78(대응 TC가 실행하지 않는 N/A뿐). 측정 대상은 26건입니다.
2. 기준 실행
   - 버그를 심지 않은 로컬 sprint5에 UI·API 전체를 돌려, 버그가 없어도 실패하는 테스트를 미리 확인했습니다(기존 결함 19건, 로컬 환경 차이 4건).
3. 버그마다 반복
   1. 심기: 로컬 서비스 코드 사본을 그 증상만 나도록 최소한으로 바꿉니다.
   2. 증상 확인: 화면이나 API에서 증상이 실제로 나는지 먼저 봅니다. 제대로 심지 못한 버그를 "발견 실패"로 세지 않기 위해서입니다.
   3. 테스트 실행
      - 대응 TC가 있는 버그: 그 TC가 든 테스트 파일과 smoke
      - 대응 TC가 없는 버그: UI 전체와 smoke. 다른 테스트가 우연히 잡는지 보기 위해서입니다. #21만 계정 잠금이 다른 테스트를 깨뜨려 로그인 관련 테스트와 API 로그인 테스트로 돌렸습니다.
   4. 판정: 아래 3번 기준으로 판정합니다.
   5. 되돌리기: 코드를 원래대로 돌리고 DB를 초기화한 뒤 smoke로 기준 상태를 확인합니다.

## 3. 판정과 원인 분류 기준
- 대응 TC: 버그가 나는 조건(화면, 항목, 로그인 상태)을 지나가고, 기대결과에 그 증상을 알아볼 확인 지점이 있는 TC
- 발견 성공: 기준 실행에서 통과하던 테스트가 버그를 심은 뒤 실패함
- 발견 실패: 실패한 테스트 목록이 기준 실행과 같음(테스트 ID 단위로 대조)
- 기준 실행에서 이미 실패하던 테스트는 판정에 쓰지 않습니다.
- 발견 실패의 원인은 TC 시트의 문구(목적, 사전 조건, 스텝, 기대결과)를 근거로 다음 중 하나로 나눕니다.
  - 스크립트 문제: 대응 TC는 있는데 스크립트가 TC보다 덜 엄격하게 확인함
  - 비슷한 TC, 다른 조건: 같은 기능의 TC는 있지만 버그가 나는 화면, 항목, 로그인 상태를 지나가지 않음
  - 비슷한 TC, 노출까지만 확인: TC 기대결과에 그 요소가 나오지만 "노출"까지만 보고, 버그가 바꾼 문구, 값, 모양은 보지 않음
  - 대응 TC 없음: 그 요소나 동작이 어떤 TC의 기대결과에도 없음
