# 교훈 기록
사용자 검수와 작업 중 바로잡힌 판단을 쌓는 파일이다. Iteration 회고 때 규칙으로 올릴지 정한다. 자동으로 읽히지 않는다.

## 1. 쓰는 법
- 언제: 노션 검수에서 반려·분류 수정이 나왔을 때, TC 수정 필요가 나왔을 때, 사용자가 판단을 바로잡았을 때
- 누가: 사라가 해당 단계(test-triage 10번, 결과 보고 등)에서 바로 쓴다.
- 형식: 맨 아래에 한 항목씩 추가한다.
```
### L-NNN YYYY-MM-DD 한 줄 요약
- 출처: 노션 행, TC ID, 대화 등
- 무엇이 틀렸나:
- 올바른 기준:
- 유형: TC 작성 | 분류 | 보고서 | 스크립트 | 기타
- 상태: 기록 | 규칙화됨(반영 위치) | 보류
```

## 2. 회고 (Iteration이 끝날 때)
1. 상태가 "기록"인 항목을 유형별로 묶는다.
2. 같은 유형이 2번 이상 나왔으면 규칙 수정안을 만든다(반영 위치: tc-write, 에이전트, 가이드). 한 번뿐인 항목은 그대로 둔다.
3. 수정안을 사용자 승인 후 반영하고, 반영한 항목을 "규칙화됨(위치)"로 바꾼다. 쓸모없어진 규칙은 같이 지운다.
4. 노션 "테스트 실행" 행에 Iteration 지표(반려 수, 분류 수정 수, TC 수정 수)를 적는다.

### L-005 2026-10-10 기능명, 기대결과, 목적, 중요도가 서로 맞지 않는 TC를 놓침

- 올바른 기준: 중요도는 기대결과가 실패했을 때의 영향으로 매기고, 기능명, 기대결과, 목적이 같은 대상을 가리키는지 함께 확인한다.
- 유형: TC 작성
- 상태: 규칙화됨(`tc-write` SKILL.md 6번 판단 점검, 사용자 요청)

### L-006 2026-10-10 인증 TC의 중요도를 입력 검증으로 낮춤

### L-007 2026-10-11 외부 도구의 대상 필터를 확인하지 않고 라이브 호출함
- 출처: schemathesis 시범(study 인계)
- 무엇이 틀렸나: `--include-method GET`과 `--include-path-regex`가 AND로 걸린다고 가정했다. 실제로는 OR로 동작해 합의한 GET 10개×5건(50건) 대신 53개 엔드포인트에 239건(쓰기 45건 포함, 모두 4xx/5xx 거부)이 나갔다.
- 올바른 기준: 외부 도구로 라이브를 호출할 때는 실행 전에 선택된 대상 목록과 예상 요청 수를 오프라인으로 확인하고, 합의 범위와 다르면 실행하지 않는다.
- 유형: 기타
- 상태: 기록

### L-008 2026-10-11 UI TC 스텝에 동작을 이동 경로로 쓰고 앞 TC 절차를 반복함
- 출처: 시트 사용자 수정(UI_82, 84, 86, 33, 39, 77)
- 무엇이 틀렸나: 이동 경로에 "[Proceed to checkout] 클릭" 같은 동작을 넣고, 앞 TC가 검증한 Billing 입력 절차를 결제 TC마다 다시 풀어 썼다. 여러 필수값 비움을 한 TC에 몰아 썼고, 열거형 기대결과를 한 줄에 몰아 썼다.
- 올바른 기준: 경로는 페이지만, 검증된 중간 절차는 경로로 생략, 다중 필드 조합은 페어와이즈로 TC 분리, 열거는 하위 불릿.
- 유형: TC 작성
- 상태: 규칙화됨(`tc-write` SKILL.md 2번 UI-TC 6, 7번, 사용자 수정 기준)

- 유형: 분류
